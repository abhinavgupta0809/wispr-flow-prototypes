      How it works

      Say the skill's name first, then whatever changes

      Proposed

      A skill has a slash name, such as /morning. Say “slash morning” at the start of a dictation to run it. You can also type the command.

      After the trigger, add the details that change: Slash morning, focus on onboarding this week.

      • Only a command at the very start counts. Dictation that just mentions a task is ordinary text.
      • Flow shows the matched skill as a chip right away, kept apart from the rest of what you said.
      • An unknown command offers Choose a skill, Create a skill, or Keep as text. Flow never guesses a workflow.
      • A misheard detail can be fixed with Phrase Repair: repeat that word, not the command.

        The proposed behavior

        Suggested after three runs, saved only when you say so

        Discovery

        • After you complete and accept the same process three times, Flow offers to save it. Three is a starting heuristic.
        • Retries, cancelled runs and repeated corrections don't count as separate runs. Changing inputs (dates, weeks, PRs) still count as the same process.
        • Flow learns only from tasks run through Flow and sources you connect. It doesn't watch other apps.
        • Review suggestion, Not now, or Don't suggest this again. Nothing is created until you accept.

        The draft skill

        • Name, slash command, sources, ordered steps, changing inputs, output, destination, and what happens at the end.
        • Dates you typed become a rule (“since the previous successful run”) when that matches what you meant.
        • Inferred recipients, destinations and reporting windows are marked for review. Flow asks only what it can't infer.
        • Try with sample data before saving. A clashing command name asks you to pick another or update that skill on purpose.

        Running it

        • Visible states: recognized, inputs ready or a missing detail, reading each source, preparing, ready for review, completed or partially completed.
        • Cancel any time. If one source fails, the rest is kept and only the failed step is retried.
        • Posting is explicit, and never repeats. A skill takes only the actions saved in it.
        • A partial run is never shown as a success.

        Setup questions

        Ask only what the runs can't answer

        Observed choices are prefilled and easy to change. Nobody re-describes the whole workflow.
        • “Which Gmail label contains the customer feedback?”
        • “Which Slack channels should this include?”
        • “Which Excel workbook, sheet, and table contain the dashboard?”
        • “Should this cover the last 24 hours or everything since your previous run?”
        • “Which metrics and thresholds should the summary highlight?”
        • “Should the result stay private, become a draft in Slack, or be posted after approval?”
        • “For PRs, should this include your repositories, assigned reviews, or both?”

        Scope boundary

        What this prototype does not show
        • No real connections. Gmail, Slack, Excel and GitHub are simulated, and every item they return is fictional sample data.
        • No real discovery. The task history is prepared; how Flow would recognize “the same process” across runs is an open design and privacy question.
        • No speech recognition. Dictations are prepared; the misheard word is marked in the demo data.
        • The summaries are written from sample data by fixed rules, not by a model. They show the intended shape, including keeping observed changes apart from possible explanations.
        • It has not been tested with users.
